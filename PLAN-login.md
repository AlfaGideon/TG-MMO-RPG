# Вход в панель с любого устройства — разбор и план

Документ-решение. Код не менялся, кроме появления этого файла.

---

## 1. Почему это происходит

Сообщение «Панель на этом устройстве ещё не видела такого игрока» — не ошибка
формы входа и не следствие неверного пароля. Это прямое следствие архитектуры.

Панель на GitHub Pages — **чистая статика**. Всё состояние (игроки, мир,
настройки, пароли) лежит в `localStorage` браузера:

```python
# webapp/backend.py
class LocalStorage:
    def __init__(self):
        from js import window
        self._ls = window.localStorage
```

Форма входа сверяет пароль со списком игроков из этого же `localStorage`:

```js
// admin-login.html
const players = state().players || {};
const me = players[uid];
if (!me) return fail("Панель на этом устройстве ещё не видела такого игрока…");
```

`localStorage` привязан к паре «браузер + устройство» и никуда не
синхронизируется. На новом устройстве он пуст: списка игроков нет, сверять
пароль не с чем. **Ни один пароль там не сработает — это неустранимо в рамках
текущей схемы.** Совет «открой как владелец и запусти бота» в другом городе
физически невыполним, вы правы.

## 2. Отдельно: это ещё и не защита

Даже там, где вход срабатывает, он ничего не охраняет:

- пароли лежат в `localStorage` **открытым текстом** (`web_admin_password`);
- проверка идёт **в браузере**, на стороне клиента;
- достаточно открыть DevTools и выполнить
  `localStorage.setItem("shadowlands_session", '{"uid":<любой>,"at":Date.now()}')` —
  и панель считает вас админом.

Для локальной демки это нормально. Для панели, открытой в интернете, — нет.
Поэтому «починить вход на Pages» и «сделать вход настоящим» — разные задачи,
и решать их одним движением не выйдет.

## 3. Ключевой факт: серверная версия у вас уже написана

В репозитории лежат **два независимых стека**, и второй уже умеет то, что нужно.

| | Стек A — Pages | Стек B — сервер |
|---|---|---|
| Код | `engine/` + `webapp/` (~5000 строк) | `bot/` + `admin/` + `core/` (~6100 строк) |
| Хранилище | `localStorage` (на устройстве) | SQLite/Postgres (`core/`, общая база) |
| Вход | JS-сверка, пароль в открытом виде | PBKDF2 100k итераций + подписанные куки |
| С другого устройства | **невозможен** | работает штатно |
| Бот | пока открыта вкладка | 24/7 (aiogram) |

Серверный `admin/auth.py` уже содержит нормальную аутентификацию:

```python
def hash_password(password):
    salt = secrets.token_hex(8)
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(), salt.encode(), 100_000).hex()
    return f"{salt}${digest}"
```

плюс `verify_password` через `hmac.compare_digest`, сессии на 30 дней,
настоящие маршруты `GET/POST /admin-login`, и роли/права, общие с ботом.
Я проверил — `admin/main.py`, `bot/main.py`, `core/models.py`, `launch.py`
компилируются без ошибок.

**Вывод: писать многопользовательский вход с нуля не нужно. Нужно развернуть
то, что уже есть.**

Важная оговорка: стеки **не делят данные**. `engine/` не импортирует `core/`,
`core/` не импортирует `engine/` (общий у них только `engine/permissions.py`).
Прогресс из `localStorage` в серверную базу сам не переедет — см. §6.

## 4. Вариант A — развернуть серверную версию (рекомендую)

**Что делаю я**

1. Чиню `render.yaml` — сейчас он **не задеплоится на free**: в нём объявлен
   persistent disk, а free-инстансы дисков не поддерживают
   ([документация Render](https://render.com/docs/free): «Free web services
   don't support… Persistent disks»). Переключаю хранилище на Render Postgres
   через `DATABASE_URL` из окружения.
2. Генерирую `ADMIN_SECRET_KEY` вместо дефолтного `change-me` — иначе куки
   сессий подписываются публично известным ключом и подделываются.
3. Прописываю `panel_url`, чтобы кнопка входа из бота вела на реальный домен.
4. Прохожу деплой, проверяю живой вход с «чистого» браузера (профиль без
   `localStorage`) и отдаю пошаговую инструкцию.

**Что делаете вы:** заводите аккаунт Render, жмёте деплой, вставляете токен
бота. Карта не требуется.

**Цена и ограничения (проверил, актуально на июль 2026)**

- Free web service **засыпает через 15 минут** без трафика, холодный старт
  ~1 минута. Для админки терпимо, для бота — нет: сообщения в простое теряются.
- Free Postgres — 1 ГБ и **истекает через 30 дней**, потом 14 дней на апгрейд,
  дальше удаление.
- Постоянная работа без сна и без экспирации базы — от **$7/мес** за инстанс
  плюс **$6/мес** за Postgres.

Честно: **бесплатно 24/7 на Render не выйдет**. Free годится проверить схему,
для боевой эксплуатации нужен платный тариф. Если бюджет нулевой — скажите,
подберу вариант под «бот 24/7 бесплатно» отдельно (у Fly.io и Railway другая
модель, но там свои оговорки).

**Итог:** настоящий вход с любого устройства, хешированные пароли, бот 24/7,
общая база. Это единственный вариант, где «доведено до ума» без кавычек.

## 5. Вариант B — оставить Pages, вынести состояние в облако

Панель остаётся статикой, но `Store` пишет не в `localStorage`, а во внешнее
KV-хранилище по HTTP.

**Что меняю:** добавляю `webapp/backend.py` → `CloudStorage` рядом с
`LocalStorage`; ключ хранилища задаётся в настройках; вход читает игроков
оттуда же. Правки локальные, стек не переписывается.

**Что это даёт:** новое устройство видит игроков, вход из другого города
проходит.

**Чего это не даёт — и это важно:**

- проверка пароля **остаётся в браузере**, обход через DevTools никуда не
  девается;
- ключ доступа к облачному хранилищу лежит в статике, то есть **виден всем**,
  кто открыл панель, — фактически база становится публичной на запись;
- бот по-прежнему живёт, только пока открыта вкладка;
- гонки записи: два устройства одновременно перезапишут состояние друг друга.

**Вывод:** снимает симптом за пару часов, но защиту не создаёт. Приемлемо,
только если панель для вас и пары доверенных людей, а данные не жалко.

## 6. Вариант C — сервер как основной, Pages как витрина

Разворачиваем сервер (как в A), а Pages-версию честно помечаем демо-песочницей
и **убираем из неё форму входа**, чтобы она не обещала невозможного. Ссылка из
бота ведёт на серверный домен.

Плюс: исчезает вторая, обманчиво-небезопасная точка входа. Минус: Pages
остаётся только демонстрацией.

Сюда же — миграция данных. Если в `localStorage` есть живой прогресс, я напишу
разовый скрипт `localStorage JSON → core/` (модели сопоставимы: `Player` ↔
`User`+`Character`, `Cell` ↔ `Cell`). Отдельная небольшая задача, делается
после деплоя. Если прогресс не важен — стартуем с чистой базы.

## 7. Сравнение

| | A: сервер | B: Pages + облако | C: A + витрина |
|---|---|---|---|
| Вход из другого города | да | да | да |
| Пароли защищены | да (PBKDF2) | нет | да |
| Обход через DevTools | закрыт | открыт | закрыт |
| Бот 24/7 | да | нет | да |
| Моя работа | ~2–3 ч | ~2 ч | ~3–4 ч |
| Ваша работа | деплой, ~15 мин | ~5 мин | деплой, ~15 мин |
| Стоимость | free для теста, ~$13/мес боевой | $0 | как A |

---

## 8. Что рекомендую

**Вариант A, при необходимости с шагом C.** Причина простая: серверный код уже
написан и компилируется — вы платите только за разворачивание, а не за
разработку. Вариант B я бы предлагать не стал: он делает вход «рабочим», не
делая его безопасным, и при этом ключ к общей базе оказывается в открытой
статике. Если панель будет доступна из интернета — это хуже текущего состояния,
где хотя бы данные не покидают устройство.

Начать имеет смысл с free-инстанса: убедимся, что вход с другого устройства
реально работает, и только потом решать про платный тариф.
